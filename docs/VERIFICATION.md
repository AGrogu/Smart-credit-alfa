## Что покрывают 46 серверных тестов

- Decimal-аннуитет и сумма выплат; ограничения двух продуктов; влияние риска и разных продуктовых политик.
- Автоматическое одобрение и отказ, неизменяемая клиентом БКИ-история, ручное рассмотрение, неполные сведения и отсутствие документа, ответ и продолжение, уменьшенное предложение, сбой и повтор.
- Принятие, отклонение, отмена, подписание и смоделированная выдача.
- Три ручных решения банка с обязательным обоснованием; запрос уточнения; рекомендация сохраняется отдельно от ручного результата.
- Снимки компании и финансов на момент рассмотрения; внутренние заметки и риск не выдаются предпринимателю.
- Разграничение компаний, документов, банковских маршрутов и уведомлений; защита от дополнительных полей, подмены компании и сценария.
- CSRF, Origin, выход/сессия, scrypt и ограничение попыток входа.
- Проверка расширений/содержимого/размера файлов; ограничение потокового тела до парсинга.
- Идемпотентное создание, конфликт повторного ключа с другим телом, повтор выдачи.
- Конкурирующие отправки, решения и выдачи: один результат, другой запрос получает конфликт; одинаковый ключ воспроизводит один результат.
- Сбой COMMIT возвращает 500 и rollback, а не ложный 201; недопустимый внутренний переход блокируется.
- Повторный lifespan/seed сохраняет записи, сессию и документы. Реальный рестарт Docker дополнительно проверен отдельным скриптом.

## 11 браузерных проверок

1. Новая заявка со всеми шагами, загрузкой и скачиванием документа; сохранение/обновление черновика; принятие → подписание → выдача → история.
2. Отказ по серверной синтетической кредитной истории.
3. Недостающая выручка → запрос → ответ → одобрение.
4. Уменьшенная сумма → принятие → подписание → выдача.
5. Временный сбой источника → повтор → одобрение.
6. Кабинет банка: фильтры, проверки, риск и рекомендация, внутренняя заметка, запрос клиенту, ответ, ручное одобрение и аудит.
7. Калькулятор второго продукта, невалидная сумма и сохранение профиля.
8. Клавиатурный переход, экран 390×844, закрытие меню, отсутствие горизонтального расширения страницы и Swagger OpenAPI 3.1.
9. Потеря ответа POST после серверного COMMIT → обновление → точное восстановление параметров без дублирования.
10. Задержанный ответ прежней компании после выхода и входа другой компанией не меняет новую сессию.
11. Создание заявки на оборудование и отклонение условий предпринимателем.

Скриншоты получены из работающего приложения: обзор, предприниматель, банк, узкий экран, вход. Показатели на них отражают накопленные синтетические заявки тестового стенда.

## Выполненный запуск и воспроизведение

Основной стенд реально запущен командой `docker compose up --build -d --wait` и доступен на `http://127.0.0.1:8080`. Из-за ограничений песочницы инструментам был предоставлен доступ к локальному Docker-сокету; служебный Docker CLI config находится только в игнорируемой папке проекта `work/docker-config`. Для обычного запуска по README этот config не нужен.

Локальный SQLite-сервер также был запущен через `scripts/run.sh`; во встроенном браузере проверены вход, обзор, начало новой заявки и сохранение первого шага. Полный автоматический E2E выполнен в Linux-контейнере, поскольку хостовый Chromium запрещен песочницей macOS (`MachPortRendezvous ... Permission denied`). Обход системной защиты не выполнялся.

Финальный браузерный прогон использовал отдельный Compose-проект `smart-credit-qa`, отдельный PostgreSQL volume и порт 8084. Только QA-конфигурация повышает лимиты входа для повторных автоматических запусков. Основной стенд сохраняет штатный лимит. Для запуска QA и тестов используйте точные команды README; они не удаляют тома и не сбрасывают данные.

## Независимое ревью и исправления

Независимый агент проверил фактический код и подтвердил критичный дефект: request-scoped cleanup мог выполнять COMMIT после ответа. Исправлено function-scoped управление транзакцией; добавлена проверка искусственного отказа COMMIT. Повторное независимое ревью подтвердило исправление.

Также исправлены сохранение тела незавершенного создания вместе с UUID, устаревшие ответы прежней сессии/карточки, навигация закрытого мастера, точные доступные имена полей, ограничение тела до multipart, локальный современный Swagger и overflow скрытой подписи таблицы. Потеря ответа, смена сессии и узкий экран проверены реальным браузером. В начале прогона выявлялись и исправлялись ошибки тестовых ожиданий (десятичный формат, ожидание смены маршрута/имена Swagger); в итоговых 11 тестах ошибок нет.

## Границы и оставшаяся неопределенность

- Проверены перечисленные сценарии; это не доказательство отсутствия всех дефектов, не пентест и не промышленная сертификация.
- Firefox, Safari, Windows, x86-64 и длительные нагрузочные/многорепличные испытания не выполнялись. Принудительный kill процесса ровно во время COMMIT, failover PostgreSQL и восстановление из резервной копии не проверялись. Изоляция COMMIT проверена внесенным сбоем, обычный рестарт обоих сервисов — фактически.
- Не проводился отдельный pip/OS vulnerability scan; зафиксированные версии и npm audit не заменяют такой аудит. Один сторонний DeprecationWarning не мешает проверкам, но требует учета при будущих обновлениях.
- Внешние реестры, БКИ, юридическая подпись и выдача денег — только описанные локальные симуляторы. Кредитные правила учебные и не валидированы для реального кредитования.
- Публикация на GitHub, доступ жюри и публичное размещение не выполнялись: отдельной авторизации и доступа нет.
- При первоначальном добавлении Swagger npm-установщик запустил Scarf postinstall; невозможно по имеющимся логам подтвердить или исключить отправку установочного отчета. Зависимость удалена, итоговая поставка содержит только статические файлы без этого установщика. Подробно: [SECURITY](SECURITY.md#аналитика-при-установке-зависимости). Это зафиксированная неопределенность приватности первоначальной установки.
